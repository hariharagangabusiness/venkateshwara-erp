# Working with this repo

- After building and end-to-end testing a requested change on the `claude/got-push-qutr7d` branch, push it, open a PR against `main`, and **merge it automatically** — do not wait for a separate "merge it" confirmation. This is a standing instruction from the repo owner (given 2026-09-29).
- Still ask for confirmation before *building* anything non-trivial when asked to (per the user's own "provide your understanding first" requests) — the auto-merge default only applies once work is built, tested, and ready to ship.
- After merging, resync the local branch with `origin/main` before starting the next task.

## Removed: Offer Word (.docx) export (2026-09-30)

Built and shipped same day (fixed-layout export, then a native-template admin-branding system via `docxtemplater`, then Equipment Reference pictures on top of that) - then removed entirely at the repo owner's request the same day, after two real problems surfaced:

- An admin uploaded the native template's own starter file unedited and activated it - since the starter's explanatory notes are real paragraphs in that `.docx`, they rendered into real customer-facing offers alongside the correctly-merged data, reading as a broken/"non-compiled" document.
- Separately, the owner asked whether the Word output could instead directly mirror the PDF's actual design (Option A, revisited). Investigated and hit a hard technical wall: the HTML→DOCX library available (`html-to-docx`) does not read `<style>` stylesheets/CSS classes at all - only inline `style="..."` attributes with a narrow supported property set (no `text-decoration`, no flexbox, no `position:fixed`/`transform` for the watermark) - so genuine parity was not achievable without rewriting `lib/offerPdf.js`'s body-HTML generation and still shipping with disclosed visual gaps. Not pursued.

Given both paths had real problems, the owner chose to drop the feature rather than keep patching it. Removed: the "Download Word" button, `GET /:id/docx`, all `/offers/docx-template*` routes, `lib/offerDocx.js`, `lib/offerDocxTemplate.js`, the "Offer Word (.docx) Template" admin panel, and the `docx`-adjacent dependencies that only that code used (`docxtemplater`, `docxtemplater-image-module-free`, `pizzip`, and the `xmldom` override that neutralized a critical CVE in the image module's own dependency - moot once that module is gone). `docx` itself stays - `lib/poDocx.js` and `lib/annexureDocx.js` (Purchase Order Word export) still use it, unaffected. The Offer PDF (`lib/offerPdf.js`) is completely untouched by any of this and remains the only export format for Offers.

`DEFAULT_OFFER_DESIGN_TOKENS.show_page_numbers` in `lib/settings.js` is now `false` - Puppeteer's `pageNumber`/`totalPages` footer classes were misaligning the footer's flex layout, so "Page X of Y" is dropped rather than fixed in place. `lib/offerPdf.js`'s `COMPANY_ADDRESS_LINES` (the static footer address/GST/phone/email block) corrected to match the repo owner's supplied reference image - the previous text had misplaced punctuation (stray semicolons inside the quoted building-type labels) and a wrong phase/plot phrase.

## Employee bulk-upload: upsert on employee_code (2026-10-01)

`POST /hr/employees/bulk-upload` (`routes/hr.js`) now upserts instead of insert-only - a row whose `employee_code` matches an existing employee UPDATEs it instead of being rejected with "already exists - skipped", so re-uploading the same filled template after changing a field (e.g. `date_of_joining`) actually applies the change. Same "blank cell never overwrites an existing value" rule as the Vendor/Item Master bulk-uploads (`routes/masters.js`) - a partial re-export/re-import can't accidentally wipe a field the file didn't carry. A row with a blank `employee_code` has nothing to match against, so it's always inserted as new, same as before. The response now includes `updated` alongside `inserted`/`skipped`/`errors` - the frontend's shared `uploadTemplateFile()` helper already displays it automatically whenever present, no UI change needed.

## Employee bulk-upload: full field set + a real pre-existing routing bug fixed (2026-10-01)

`EMPLOYEE_TEMPLATE_COLUMNS` now covers every field on the Add Employee form (21 columns: employment_type, PAN, blood group, emergency contact, bank name/account/IFSC, Aadhaar, passport, visa, driving license - not just the original 10), so a one-time migration of existing employee data can be done entirely via the template instead of hand-entering the rest afterward per employee. `employment_type` is validated against the same 4 values the Add Employee form's dropdown offers (Full-time/Contract/Probation/Intern) - an unrecognized value errors that row rather than silently accepting garbage; a new "Employment Types" reference sheet lists them, same pattern as the existing "Departments" sheet. Deliberately drops the legacy `bank_account` column from the template - the Add Employee form itself doesn't use it either (it writes `bank_name`/`account_number`/`ifsc_code`); that column still exists in the schema for old data and stays editable via the Edit Employee screen.

While testing this, found and fixed a real pre-existing bug unrelated to the field-set change: `GET /employees/template` was registered *after* `GET /employees/:id` in `routes/hr.js`, and Express matches routes in registration order - `:id` matches literally any path segment including the string `"template"`, so every request for the template was being swallowed by the `:id` handler, which looked up an employee with id `"template"`, found none, and returned a plain `{"error":"Not found"}`. **"Download Template" had never actually worked** since the bulk-upload feature first shipped (2026-09-29) - this was caught only because testing the extended template surfaced it. Fixed by moving the `/employees/template` route before `/employees/:id`.

## Vendor Download Template fix + Vendor/Stock bulk-upload field parity (2026-10-01)

The exact same route-shadowing bug as above also existed in `routes/masters.js`: `GET /vendors/template` was registered after `GET /vendors/:id`, so "Download Template" on the Vendors page always 404'd ("Not found") - reported by the repo owner directly (screenshot showed the raw alert). Fixed the same way: `/vendors/template` and `/vendors/bulk-upload` now registered before `/vendors/:id`. Audited every other GET route in `routes/masters.js` and `routes/purchase.js` for the same `:id`-before-literal-sibling pattern (Item Master, Stock Movements, Purchase Orders, Purchase Requests, RFQ inbox, Store Challans) - no other instance found.

`VENDOR_TEMPLATE_COLUMNS`/the vendor bulk-upload were also missing `status` (the Add Vendor form's only field not yet on the template) - added, validated against the same 3 values the form's dropdown offers (Active/Inactive/Blacklisted) with a new "Status Values" reference sheet, same pattern as Employee's "Employment Types" sheet. Item Master's template already covered every Add Item field - no gap there.

Stock In/Out (`routes/purchase.js`'s `/store/movements/template` and `/store/movements/bulk-upload`) was missing `department`, `project`, `client` - the Issue (OUT) screen's own fields, which the bulk-upload template didn't expose at all even though `department` is a hard-required field there (`/store/issue` rejects a request with no `department_id`). All three are name-matched (department/client by exact name, project by Project Code or title) and apply to OUT rows only, mirroring the interactive Receive/Issue forms exactly (Receive only has `po_no`; Issue has department/project/client, not `po_no`) - `department` is required and a hard error if missing or unrecognized on an OUT row; given on an IN row, it's ignored with a warning (same pattern `po_no` already used for the wrong movement type); `project`/`client` are optional on OUT and likewise ignored-with-warning on IN.

## Click-to-sort column headers: Employee list (2026-10-01)

New generic `sortableTableHTML(key, columns, rows, rowRenderer, onSort)` helper in `public/js/app.js`, added alongside (not replacing) the existing `tableHTML()` - every other page using `tableHTML()` is untouched. Follows the same "caller supplies a re-render callback" idiom as `LIST_SEARCH_STATE`/`filterList`: clicking a header only redraws the table into whatever DOM node `onSort` targets, not the whole page, so e.g. in-progress typing in the Add Employee form above the table survives a sort click (a full-page re-render via `navigate()` would have wiped it). Sort state persists per `key` for the session - leaving the Employees page and coming back keeps the last sort applied. Wired into the Employees list (`#emp-table-container`) across all 7 data columns (Code/Name/Department/Designation/Type/Salary/Status - Salary sorts numerically, the rest case-insensitive string; Action is not sortable). Not yet wired into any other list page - only Employees was asked for.

## Item Price History + Purchase Order approval gate (2026-10-02)

Prompted by a review of the legacy desktop ERP's Purchasing/Store & Inventory menus against this app - full gap list (Purchase Invoice/AP booking, Purchase Schedule, RM Requirement Sheet, BOM/Production Voucher, Batch Creation, Consumption Slip, FG Packing/Dispatch, Sale Rejection MRN) recorded in that conversation for a later phased build; only the two pieces below were actually asked for this round.

**Item Price History** - no new table: `purchase_orders` already carries `item_id`/`vendor_id`/`rate`/`created_at` per line (one row per PO line), so `GET /purchase/items/:itemId/price-history?from=&to=` (default last 1 year, caller-overridable) is a pure read against existing data. A "Price History" link sits next to the item picker on New Purchase Order and New Purchase Request line items, and on the Item Master list - opens a modal (`showItemPriceHistory()` in `public/js/app.js`) showing every past PO for that item (vendor, rate, qty, date, status - cancelled/rejected included and flagged, not hidden) with lowest/highest/latest summary stats. Since a PO here is one vendor for every line (single `<select id="po-vendor">`, not per-line), the New PO modal adds a "Use this vendor" button per row that writes straight into that select - this is how price history actually drives the vendor choice, not just informs it (omitted from the Purchase Request context, which has no vendor field). The existing crude vendor-suggestion box under the PO line items (`showVendorsForPOLines()`, previously just a category match) now also annotates each suggested vendor with its last rate and date, pulled from the same endpoint.

**Purchase Order approval gate** - Purchase Orders had *zero* approval gate before this (only Purchase Requests did) - `POST /orders` created a live, receivable, emailable PO instantly. New `PurchaseOrder` approval chain (bootstrapped idempotently in `db/index.js`'s `bootstrapPurchaseOrderApproval()`, called from `server.js` on every boot, same pattern as `bootstrapForeignPayments()`): step 1 is the Purchase department's own HOD (role `Purchase` + `requires_supervisor=1` - there's no separate "Purchase HOD" role, same is_supervisor-flag model every other HOD check in this app already uses), always required; step 2 is `Management`, gated by order value (default ₹50,000, admin-editable from the existing Approval Matrix page - no new UI needed there, the new chain just appears in it). A PO now starts at `PendingApproval` and only becomes `Open` (receivable, emailable) once the chain clears; `/store/receive`, the stock bulk-upload's PO lookup, and `GET/POST /orders/:id/{pdf,docx,email}` all block on `PendingApproval`/`Rejected`. The bulk Open-PO migration importer (`POST /orders/bulk-upload`, for bringing already-live legacy POs into the system) is deliberately untouched - those aren't new orders being raised through this system, so they skip the gate entirely, same as before.

Editing a PO (any field, any status short of Received/Cancelled) now **always** sends it back through approval from scratch - a prior sign-off doesn't carry over, and the audit log (already-existing `togglePOHistory` UI, `routes/purchase.js`'s `poAuditLog()`) records the exact field diff against a `po_edit_resubmit` action, so "what changed and why it's back in the queue" is visible with zero new frontend work. A still-live previous approval (one nobody's finished acting on) is marked `Superseded` so it can't double up in anyone's queue; an already-`Approved` one is left alone as an honest historical record. Cancelling a PO also cancels its live approval the same way Purchase Request cancellation already does.

Sending a vendor a PDF/Word copy or email while `PendingApproval` is hard-blocked by default; a new Purchase Settings checkbox (`allow_pending_po_email`, off by default) lets an Admin lift that for a genuinely urgent case - when lifted, `lib/poPdf.js`/`lib/poDocx.js` both render a visible red "PENDING APPROVAL - not yet authorized" banner on the document itself, so it can never be mistaken for an authorized commitment.

## Price History button alignment + full PO context for approvers (2026-10-02)

Two follow-ups to the above, same day. The "Price History" link next to an item picker (New PO/PR line items) used to drop onto its own line below the picker, since `itemPickerHTML`'s wrapper is a full-width block - now wrapped in a `display:flex;align-items:center` row with the picker at `flex:1`, so the button sits beside the field instead of stacked under it.

The "My Approvals" drill-down (`renderApprovalDrilldown()` in `public/js/app.js`) gained a `purchase_order` branch alongside its existing per-entity-type ones (purchase_request, expense_voucher, leave_request, ...) - an approver clicking "Details" on a PO now sees everything needed to decide, not just the one-line summary: vendor name/GSTIN/contact, every term (payment terms, delivery date, our address, LD rate/cap/trigger notes, additional terms), the full line-item table (item/qty/rate/HSN/GST/total/status) with its own taxable/GST/grand-total rollup, and a per-line "Price History" button so the approver can judge whether a quoted rate is reasonable without leaving the approval queue - plus the same attachments widget already wired up for every other approval type (`attachType = 'purchase_order'`). Built entirely from `GET /orders` (already returns every column needed, joined) and `GET /masters/vendors/:id` - no new backend route.
