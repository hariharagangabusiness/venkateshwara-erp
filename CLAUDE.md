- After building and end-to-end testing a requested change on the `claude/got-push-qutr7d` branch, push it, open a PR against `main`, and **merge it automatically** — do not wait for a separate "merge it" confirmation. This is a standing instruction from the repo owner (given 2026-09-29).
- Still ask for confirmation before *building* anything non-trivial when asked to (per the user's own "provide your understanding first" requests) — the auto-merge default only applies once work is built, tested, and ready to ship.
- **"Provide your understanding before you execute, wait for my confirmation" applies to every ask, standing, not just the ones where the owner says it that turn.** Restated explicitly 2026-10-08 ("this step needs to be in memory for all the ask") after it had already been the working pattern all session - research/diagnose first, write up findings and the proposed fix per item, and wait for an explicit go-ahead before touching code, for every request this size or larger, not only when the request happens to repeat the phrase.
- **Any new sidebar page (a new entry in `NAV` in `public/js/app.js`) must also be added to `lib/pageCatalog.js`'s `PAGE_CATALOG`** in the same round - that catalog is the only source of checkable options on the User Access screen, and a page missing from it can never be granted to a role an Admin has explicitly configured (restricted) there, silently vanishing from that role's sidebar with no error anywhere. Standing rule since 2026-10-08, after this was missed twice (HR Compensation's 3 pages on 2026-10-04, then FG Dispatch/MRN/Credit Notes on 2026-10-04 again) and only caught on a full audit prompted by the owner on 2026-10-08.
- After merging, resync the local branch with `origin/main` before starting the next task.
- **Collapse-by-default is mandatory for any new multi-item, grouped, or repeating list UI** going forward - default state collapsed with an explicit expand control, never auto-expanded on page load. Standing rule since 2026-10-07 (prompted by a multi-line Purchase Order dumping all of its lines onto the page uncollapsed), extending the same discipline already applied to the sidebar nav, specific list panels (2026-10-01), and the To-Do board (2026-10-06).
- **Any expandable/dropdown/overlay field (search pickers, menus, anything that grows beyond its collapsed size) must have its actual rendered width verified before shipping** - not just eyeballed, and not just checked for ancestor overflow-clipping. Measure it (e.g. a Playwright `getBoundingClientRect()` check) against realistic sibling content (another button or column next to it competing for the same row's width), since a sibling can squeeze a flexible picker down to illegibility even when nothing is clipping it. Standing rule since 2026-10-07, after the PR/PO item-search dropdown was fixed for clipping once (2026-10-04) and then "resurfaced" as a width-squeeze from an unrelated sibling element added later.

## Removed: Offer Word (.docx) export (2026-09-30)

Built and shipped same day (fixed-layout export, then a native-template admin-branding system via `docxtemplater`, then Equipment Reference pictures on top of that) - then removed entirely at the repo owner's request the same day, after two real problems surfaced:

- An admin uploaded the native template's own starter file unedited and activated it - since the starter's explanatory notes are real paragraphs in that `.docx`, they rendered into real customer-facing offers alongside the correctly-merged data, reading as a broken/"non-compiled" document.
- Separately, the owner asked whether the Word output could instead directly mirror the PDF's actual design (Option A, revisited). Investigated and hit a hard technical wall: the HTML→DOCX library available (`html-to-docx`) does not read `<style>` stylesheets/CSS classes at all - only inline `style="..."` attributes with a narrow supported property set (no `text-decoration`, no flexbox, no `position:fixed`/`transform` for the watermark) - so genuine parity was not achievable without rewriting `lib/offerPdf.js`'s body-HTML generation and still shipping with disclosed visual gaps. Not pursued.

Given both paths had real problems, the owner chose to drop the feature rather than keep patching it. Removed: the "Download Word" button, `GET /:id/docx`, all `/offers/docx-template*` routes, `lib/offerDocx.js`, `lib/offerDocxTemplate.js`, the "Offer Word (.docx) Template" admin panel, and the `docx`-adjacent dependencies that only that code used (`docxtemplater`, `docxtemplater-image-module-free`, `pizzip`, and the `xmldom` override that neutralized a critical CVE in the image module's own dependency - moot once that module is gone). `docx` itself stays - `lib/poDocx.js` and `lib/annexureDocx.js` (Purchase Order Word export) still use it, unaffected. The Offer PDF (`lib/offerPdf.js`) is completely untouched by any of this and remains the only export format for Offers.

## Item Price History + Purchase Order approval gate (2026-10-02)

Prompted by a review of the legacy desktop ERP's Purchasing/Store & Inventory menus against this app - full gap list (Purchase Invoice/AP booking, Purchase Schedule, RM Requirement Sheet, BOM/Production Voucher, Batch Creation, Consumption Slip, FG Packing/Dispatch, Sale Rejection MRN) recorded in that conversation for a later phased build; only the two pieces below were actually asked for this round.

**Item Price History** - no new table: `purchase_orders` already carries `item_id`/`vendor_id`/`rate`/`created_at` per line (one row per PO line), so `GET /purchase/items/:itemId/price-history?from=&to=` (default last 1 year, caller-overridable) is a pure read against existing data. A "Price History" link sits next to the item picker on New Purchase Order and New Purchase Request line items, and on the Item Master list - opens a modal (`showItemPriceHistory()` in `public/js/app.js`) showing every past PO for that item (vendor, rate, qty, date, status - cancelled/rejected included and flagged, not hidden) with lowest/highest/latest summary stats. Since a PO here is one vendor for every line (single `<select id="po-vendor">`, not per-line), the New PO modal adds a "Use this vendor" button per row that writes straight into that select - this is how price history actually drives the vendor choice, not just informs it (omitted from the Purchase Request context, which has no vendor field). The existing crude vendor-suggestion box under the PO line items (`showVendorsForPOLines()`, previously just a category match) now also annotates each suggested vendor with its last rate and date, pulled from the same endpoint.

**Purchase Order approval gate** - Purchase Orders had *zero* approval gate before this (only Purchase Requests did) - `POST /orders` created a live, receivable, emailable PO instantly. New `PurchaseOrder` approval chain (bootstrapped idempotently in `db/index.js`'s `bootstrapPurchaseOrderApproval()`, called from `server.js` on every boot, same pattern as `bootstrapForeignPayments()`): step 1 is the Purchase department's own HOD (role `Purchase` + `requires_supervisor=1` - there's no separate "Purchase HOD" role, same is_supervisor-flag model every other HOD check in this app already uses), always required; step 2 is `Management`, gated by order value (default ₹50,000, admin-editable from the existing Approval Matrix page - no new UI needed there, the new chain just appears in it). A PO now starts at `PendingApproval` and only becomes `Open` (receivable, emailable) once the chain clears; `/store/receive`, the stock bulk-upload's PO lookup, and `GET/POST /orders/:id/{pdf,docx,email}` all block on `PendingApproval`/`Rejected`. The bulk Open-PO migration importer (`POST /orders/bulk-upload`, for bringing already-live legacy POs into the system) is deliberately untouched - those aren't new orders being raised through this system, so they skip the gate entirely, same as before.

Editing a PO (any field, any status short of Received/Cancelled) now **always** sends it back through approval from scratch - a prior sign-off doesn't carry over, and the audit log (already-existing `togglePOHistory` UI, `routes/purchase.js`'s `poAuditLog()`) records the exact field diff against a `po_edit_resubmit` action, so "what changed and why it's back in the queue" is visible with zero new frontend work. A still-live previous approval (one nobody's finished acting on) is marked `Superseded` so it can't double up in anyone's queue; an already-`Approved` one is left alone as an honest historical record. Cancelling a PO also cancels its live approval the same way Purchase Request cancellation already does.

Sending a vendor a PDF/Word copy or email while `PendingApproval` is hard-blocked by default; a new Purchase Settings checkbox (`allow_pending_po_email`, off by default) lets an Admin lift that for a genuinely urgent case - when lifted, `lib/poPdf.js`/`lib/poDocx.js` both render a visible red "PENDING APPROVAL - not yet authorized" banner on the document itself, so it can never be mistaken for an authorized commitment.

## Accounts Payable: Purchase Invoice booking, vendor payments, credit notes (2026-10-02)

Prompted by the Purchase & Store gap review earlier the same day (Phase A of a six-phase list covering Accounts Payable, Demand Planning, Production & Consumption, Returns & Rejections, Dispatch & Packing, and Reporting - the rest remain unbuilt, for a later round). Mirrors the existing Sales Invoice module's own patterns throughout rather than inventing new ones.

**Schema** - three new tables (`purchase_invoices`, `purchase_invoice_items`, `vendor_credit_notes`) in `db/index.js`. A Purchase Invoice bills against a specific PO line's received-but-not-yet-invoiced quantity - `poLineBillableQty()` in `routes/finance.js` computes `poReceivedQty(lineId) - SUM(already-invoiced qty on non-cancelled invoices)`, so a line can never be billed past what's physically been received, and the New Purchase Invoice form's line picker (`billable-po-lines` endpoint) only ever offers that remainder. `poReceivedQty()` itself was pulled out of `routes/purchase.js` into a new shared `lib/purchaseOrders.js`, since both routes now need it.

**Approval gates payment, not booking** - a Purchase Invoice starts at `PendingApproval` the moment it's booked and runs through a new `PurchaseInvoice` approval chain (step 1: Accounts department HOD, `role=Accounts` + `requires_supervisor=1`, always required; step 2: Management, gated by the same ₹50,000 default threshold as the Purchase Order chain, admin-editable from the existing Approval Matrix page) - `bootstrapPurchaseInvoiceApproval()` in `db/index.js`, called from `server.js` on every boot like its PO-chain sibling. `POST /purchase-invoices/:id/record-payment` is hard-blocked until status is `Approved` or `PartiallyPaid` - mirrors Expense Voucher's own "approval gates the payment, not a separate per-instalment cycle" model. Paid/due are always computed live by summing `finance_ledger` rows (`type='PurchaseInvoice'`) rather than a stored running-total column, so partial payments can never drift out of sync with reality - same reasoning already used everywhere else in this codebase that tracks a running total against a source document.

**TDS and GST** - `tds_rate`/`tds_amount` on the invoice (`tds_amount = taxable_value * tds_rate/100`, deducted on the base amount, not the GST-inclusive total, matching how TDS actually works); `net_payable = total_value - tds_amount` is what's tracked for payment purposes. GST split is CGST+SGST vs IGST based on vendor state vs company state, same comparison Sales Invoices already do, just reversed (buyer vs company there, vendor vs company here).

**Vendor Credit Notes** reduce what's payable on a specific invoice (rate corrections, short-shipments, etc.) - `purchaseInvoiceCreditedAmount()` sums active (non-cancelled) notes, due = `net_payable - paid - credited`, and an invoice auto-flips to `Paid` the moment paid+credited fully covers it. Cancelling a credit note reverts the invoice's status back down if it's no longer fully covered.

**Reporting** - new `GET /pending-purchase-bills` (AP aging: `due_date = booking_date + vendor.payment_terms_days`, `days_overdue` computed live, cancelled/fully-paid invoices excluded). The pre-existing GST Summary report's Input Tax Credit figure, previously an approximation sourced from `purchase_orders.gst_amount` (a mere commitment, not a tax document), now sources from real booked `purchase_invoices` - a natural accuracy fix enabled by this table existing at all.

**Frontend** - new "Purchase Invoices (AP)" page (`PAGES['purchase-invoices']` in `public/js/app.js`): booking form with a PO-driven line-item picker, collapsible Purchase Invoices / Vendor Credit Notes / Pending Purchase Bills panels, per-invoice Details/Record Payment/Credit Note/Cancel actions gated by status, and the generic attachments widget (`purchase_invoice` added to `routes/attachments.js`'s `VALID_TYPES`) for attaching the scanned vendor bill. The "My Approvals" drill-down (`renderApprovalDrilldown()`) gained a `purchase_invoice` branch alongside the existing `purchase_order` one - full vendor/bill/line-item/GST/TDS context plus a per-line Price History button, so an approver never has to leave the queue to judge a bill.

**Bug found and fixed while building this** - the exact same `:id`-before-literal-sibling route-shadowing bug already hit twice before in this codebase (Employee and Vendor "Download Template" routes, both logged above) showed up a third time, this time self-inflicted: `GET /purchase-invoices/:id` was registered before `GET /purchase-invoices/billable-po-lines` in `routes/finance.js`, so Express's `:id` matched the literal string "billable-po-lines" first and the New Purchase Invoice form's line picker always 404'd. Caught during this round's own end-to-end testing (not reported by anyone) and fixed the same way as before - the literal route moved ahead of the `:id` one, with a comment explaining why, so it doesn't happen a fourth time.

## Employee HR: Referral Incentives, Exit tracking, Salary Hike Cycles (2026-10-04)

Scoped over two rounds - a full design proposal with 4 open questions, confirmed by the owner, then a scheduled check-in to re-confirm the locked scope before building (per the standing "ask before building anything non-trivial" rule). The 4 locked answers: (1) a referral incentive is forfeited if the referred employee exits before completing probation; (2) probation duration is configurable per employee at hire time, not a fixed global default; (3) the hike approval chain is two-step, mirroring Purchase Request's HOD->Management shape; (4) HODs see their own department's hike/salary view (oversight-scoped), Admin/Management see everything.

**Schema** - `employees` gains `referred_by_employee_id`, `referral_incentive_amount`, `probation_end_date` (set at hire time), `exit_reason`/`exit_recommendation` (set on Edit Employee when status moves to resigned/terminated). Three new tables: `referral_incentives` (one row per referred hire, not per referrer), `salary_hikes` (permanent per-employee hike history, Manual or Cycle-sourced), `salary_hike_cycles` + `salary_hike_cycle_items` (the annual planning run).

**Who approves what - a deliberate departure from "HOD proposes"'s literal reading.** This codebase's existing cross-department chains (ExpenseVoucher, Leave, PurchaseInvoice) all route to ONE fixed owning department's HOD, never to "whichever department the entity happens to belong to" - there's no per-raiser-department-HOD step in the generic approval engine (`lib/approvals.js`'s `canAct()` matches a single `approver_role_id` per step), and adding one would be a much larger change for comparatively little benefit here. So "HOD" in the locked design means the HR department's own HOD specifically (role `HR` + `requires_supervisor=1`) - HR already owns and builds both the referral payout and the hike cycle, same as how Accounts owns every Purchase Invoice. `bootstrapHrCompensationApprovals()` in `db/index.js` (called from `server.js` after seed, same pattern as every other chain bootstrap) creates two chains: `ReferralIncentive` (single step, HR HOD only - a referral payout is a modest, routine amount) and `SalaryHikeCycle` (HR HOD then Management, Management's step unconditional at `min_amount=0` rather than value-gated like PO/PI's ₹50,000 threshold, since an annual compensation decision affects the whole org regardless of its total value).

**Referral Incentives** - status flow `PendingProbation` (set automatically when an employee is added with a referrer and incentive amount - no separate "create referral" action) -> `Eligible` (new `lib/referralIncentiveScan.js`, 6-hourly on the same timer as the BG/SOA/BOE scans in `server.js`, flips once `probation_end_date` has passed and the referred employee is still active - deliberately does NOT also auto-start the approval, so HR can confirm the referral terms still hold first) -> `PendingApproval` (explicit HR "Submit for Approval") -> `Approved`/`Rejected` -> `Paid` (explicit HR mark-paid with a payment reference, same pattern as Purchase Invoice's record-payment). `Forfeited` is NOT scan-driven - it's set inline the moment the referred employee's own status becomes resigned/terminated (`routes/hr.js`'s employee PUT route), so it's immediate rather than waiting up to 6 hours for the next scan, and it also cancels any live approval the same way PO/PI cancellation already does.

**Salary Hike Cycles** - `Draft` (HR builds `salary_hike_cycle_items`, either one employee at a time or bulk-applying a %/fixed hike across a department or org-wide - each item snapshots `current_salary` at the moment it's set, not read live again later, so what an approver reviewed is what gets applied even if someone edits that employee's salary elsewhere in the gap) -> `PendingApproval` -> on final `Approved`, `routes/approvals.js`'s `syncEntityStatus` atomically writes one `salary_hikes` row per item AND updates each employee's `monthly_salary`, then flips the cycle straight to `Applied` in the same transaction - there's no separate manual "apply" action, since by the time Management has signed off there's nothing left for a human to decide. A `Rejected` cycle isn't dead - `POST /salary-hike-cycles/:id/reopen` puts it back to `Draft` for editing and resubmission, same "fix and try again" spirit as a Purchase Request's reject-edit-resubmit cycle, just without needing a brand new cycle row (the rejected approval and its comment stay as an honest historical record).

**Salary Report** (`GET /hr/salary-report`) - department-wise and org-wide headcount/total/min/max, optionally compared against a given cycle's proposed figures. Admin/Management see every department; anyone else needs to be a supervisor, and then only sees their own home department plus anything granted via `lib/roleOversight.js`'s existing oversight-grant model (same "HOD who covers two departments in the real org" mechanism `routes/todos.js` already uses) - a department outside that set 403s rather than silently filtering.

**Deliberately not built this round**: a `salary_hikes`/`referral_incentives` attachments widget, and a bulk-upload path for the new Add Employee referral fields (the existing Employee Master bulk-upload template is for the full field set; `referred_by_employee_id` et al. are hire-time-only fields entered once per employee, not something that benefits from a spreadsheet round-trip the way the original 21-column migration template did). A standalone `salary_hikes` bulk-upload template DOES exist (`GET /hr/salary-hikes/template`) - for backfilling historical hike records only, it explicitly does not touch `employees.monthly_salary`.

## FG Dispatch + Sale Rejection MRN (Purchase gap-review Phases D & E) (2026-10-04)

Prompted by the same Purchase/Store gap review that produced Accounts Payable (2026-10-02) - Phase D (Returns & Rejections) and Phase E (Dispatch & Packing) from that six-phase list, the next two phases picked up. Scoped over two rounds, same discipline as HR Compensation: a design proposal, the owner's 4 locked answers, then a full re-confirmation of the revised design before building (the owner's explicit "provide your understanding before executing - take my confirmation" on this round). The 4 locked answers: (1) a Sales Order is not always one bespoke line - it can have multiple lines and multiple partial dispatches for big projects, so the whole feature had to be designed around that, not a single-shipment assumption; (2) FG Dispatch needs two-step approval, Accounts then Management; (3) a hard payment block on dispatch, overridable only by Management; (4) a rejection's resolution (credit note vs. replacement) is never automatic - always an explicit HR/Sales choice, with FOC replacement riding the existing FOC approval flow rather than a new one.

**Sales Order line items are a retrofit, not a replacement.** New `sales_order_items` table is purely additive - an SO with no rows behaves exactly as before (`order_value` stays a manually-entered number); the moment a line is added, `order_value` is recomputed as the sum of the lines (`recomputeOrderValue()` in `routes/sales.js`) and the manual field is ignored going forward. `routes/offers.js`'s offer-confirm transaction now also copies `offer_items` straight into `sales_order_items` at SO-creation time, so an SO born from a multi-line Offer already carries its lines with no extra step. `item_id` on a line stays optional - "Finished Goods" isn't a concept anywhere else in this codebase (confirmed by research before building), and most lines here are custom-fabricated, free-text equipment, not a stock-tracked item.

**Billable/dispatchable-quantity discipline, carried one level deeper than Purchase Invoice's.** This codebase already has one proven pattern for "how much of this line is still available to act on" (`poLineBillableQty()`, Purchase Invoice vs. PO line, 2026-10-02) - `lib/soItems.js` applies the same reasoning twice, chained: `soLineDispatchableQty()` = ordered qty minus whatever's already claimed by any non-Rejected/non-Cancelled dispatch (so a dispatch still sitting in `PendingApproval` reserves its quantity exactly like an already-`Dispatched` one - nobody can over-commit a line across two simultaneous dispatches), and `dispatchItemRejectableQty()` = dispatched qty minus whatever's already claimed by a non-cancelled MRN, the identical reservation logic one level down. Editing a quantity down on an SO line is blocked once dispatches exist against it (`PUT /orders/:id/items/:itemId` rejects a reduction below what's already been dispatched, with the exact blocking quantity in the error).

**FG Dispatch - two-step Accounts->Management, always required, not value-gated.** New `FgDispatch` approval chain (`bootstrapSalesFulfillmentApprovals()` in `db/index.js`, called from `server.js` on boot like every other chain bootstrap) - step 1 Accounts HOD (role `Accounts` + `requires_supervisor=1`), step 2 Management, both at `min_amount=0` so neither step is skippable regardless of dispatch value (same "always required" shape as HR's SalaryHikeCycle Management step, not the ₹50,000-gated PO/PI pattern). A dispatch starts `PendingApproval` and only becomes `Dispatched` (and reduces what's left `soLineDispatchableQty`) once the chain clears. On final approval, `routes/approvals.js`'s `syncEntityStatus` directly flips the project's `Packing` and `Shipping` job_cards to `Completed` (raw DB writes bypassing the interactive PATCH route's human-actor checks, since this transition is system-triggered) and calls `advanceProjectStatus()`/`releaseDependents()` from `lib/pipeline.js` for each - dispatch approval is the event that actually finishes those two stages, not a separate manual job-card update.

**Hard payment gate, Management-only override, with a real permission bug found and fixed mid-build.** `unpaidPreDispatchProforma(salesOrderId)` in `routes/sales.js` checks for a `proforma_invoices` row (`invoice_type='PreDispatch'`, status not `Received`/`Cancelled`) against the order; if found, `POST /sales/dispatches` is blocked unless `req.user.role_name` is `Management` or `Admin`. Testing the override as `management1` hit `"Access denied: missing permission sales_order.manage"` - Management had zero Sales-domain permissions in this codebase before this feature, so the role-based override check in application code was unreachable regardless of how correctly it was written; the route-level permission gate stood in front of it. Fixed by granting Management the `sales_order.manage` permission inside `bootstrapSalesFulfillmentApprovals()` (idempotent `INSERT OR IGNORE`, same pattern as the existing `bootstrapBgManageGrant()`). An override is recorded on the dispatch itself (`payment_override_by`/`payment_override_note`) and surfaces as a red banner in both the FG Dispatch page and the My Approvals drilldown, so an overridden dispatch is never mistaken for a normally-cleared one.

**Sale Rejection MRN - single-step Sales HOD, tied to a specific dispatched line.** New `SaleRejectionMRN` chain (role `Sales` + `requires_supervisor=1`, single step - a rejection is Sales' own call, not a cross-department one). An MRN can only be raised against a fully `Dispatched` shipment and only for quantity still `dispatchItemRejectableQty()`-available on that dispatch line, same reservation discipline as above. Both `FgDispatch` and `SaleRejectionMRN` deliberately route to one FIXED owning department's HOD (Accounts/Management for dispatch, Sales for MRN) rather than "whichever department raised it" - the same departure from a literal "HOD approves their own team's request" reading already documented for HR's ReferralIncentive/SalaryHikeCycle chains, because this codebase's generic approval engine (`lib/approvals.js`'s `canAct()`) only matches one fixed `approver_role_id` per step; there's no per-raiser-department routing anywhere in it.

**Resolution is always a manual, explicit choice - never automatic.** `sale_rejection_mrns.resolution` starts `'Unresolved'` and changes only via `POST /mrns/:id/resolve-credit-note` or `POST /mrns/:id/resolve-foc`, both guarded against double-resolution. **Sales Credit Note** mirrors the existing Vendor Credit Note's own GST-split-by-state logic (CGST+SGST if buyer state matches company state, else IGST), sourced from the SO's live Sales Invoice's `buyer_state`. **FOC Replacement rides the pre-existing FOC approval flow rather than a new chain** - `foc_requests` gained one new column, `source_mrn_id`, purely for traceability back to the MRN that spawned it; the resolution route just inserts an ordinary FOC request row. Cancelling a credit note reverts its MRN back to `Unresolved` so it can be re-resolved; following the same "derive, don't duplicate" reasoning used throughout this codebase, the MRN carries no forward reference to either the credit note or the FOC request - both are found by a reverse `WHERE source_mrn_id = ?` / `WHERE sale_rejection_mrn_id = ?` lookup instead.

**Frontend** - New Sales Order's line-items grid (`SO_LINES` state, `renderSOLines()`/`addSOLine()`), an "Items" toggle per order row for adding/removing lines after creation (quantity-reduction guard enforced server-side), and three new pages: FG Packing & Dispatch (`PAGES['fg-dispatches']`), Sale Rejection MRN (`PAGES['sale-rejection-mrns']`), and Sales Credit Notes (`PAGES['sales-credit-notes']`). The My Approvals drill-down (`renderApprovalDrilldown()`) gained `fg_dispatch` and `sale_rejection_mrn` branches alongside the existing ones, each showing full line-item/payment-override/rejection-reason context plus the standard attachments widget (`fg_dispatch`/`sale_rejection_mrn` added to `routes/attachments.js`'s `VALID_TYPES`) - an approver never has to leave the queue to see what they're deciding on, same standard every other entity type in this drilldown already meets.

**End-to-end tested** via a scratch server covering the full lifecycle both at the API level (multi-line SO creation with computed order_value, partial/multiple dispatches with quantity reservation across both levels, the two-step approval chain with job-card auto-completion verified by direct DB query, the payment gate block and its Management-only override including the permission-grant fix, single-step MRN approval, both resolution paths with correct GST math and `source_mrn_id` linkage, double-resolution blocking, credit-note-cancel-reverts-resolution, dispatch PDF generation, and the SO-item quantity-reduction guard) and with a Playwright pass across every new/changed page and the My Approvals drilldown for both new entity types at every approval step.

## Purchase Requests / Purchase Orders page-load performance fix (2026-10-04)

Reported directly by the repo owner: Purchase Request and Purchase Order pages took noticeably longer to load than other pages like Offers/Quotations. Investigated and found two distinct, compounding causes in `public/js/app.js`, neither involving the backend.

**Un-parallelized API calls.** `PAGES.offers` already fires its startup reads as one `Promise.all`, so its total load time is the slowest of the 3 calls. `PAGES['purchase-requests']` and `PAGES['purchase-orders']` instead `await`ed each call one after another - 6 and 7 independent reads respectively (`/purchase/requests`, `/masters/items`, `/projects`, `/settings/purchase-quote-threshold`, `/purchase/rfq-inbox`, plus `fetchPanelOrder()`'s own `/dashboard/layout/...` read for PR; `/purchase/orders`, `/masters/vendors`, `/masters/items`, `/purchase/requests`, `/settings/company-addresses`, `/settings/purchase`, plus `fetchPanelOrder()` for PO) - with none of them depending on another's result. Total wait time was the *sum* of 6-7 round trips instead of their *max*. Both pages now fire all of their reads as one `Promise.all`, including the panel-order read - `fetchPanelOrder()` only needs each page's panel keys, which are static and known without waiting on any of the data, so it no longer has to come last.

**Purchase Orders also built a full hidden Edit form for every row on every load, regardless of whether anyone opened it.** `renderPORows()` called `poEditForm(o)` (and `poTermsForm(o)`) unconditionally for every PO row - and every line of a multi-line PO - into a `display:none` panel. `poEditForm()` embeds a full `<select>` of every Active vendor plus the full searchable item picker (an `<option>` for every item in Item Master), so with N orders and M vendors/items on file this was O(N×M) HTML string-building and DOM nodes created purely for panels most users never open on a given visit. Purchase Requests never had this problem - its own Edit form (`openEditPR`) was already built lazily into one shared panel on first click. `poEditForm`/`poTermsForm` now build the same way: `renderSinglePORow`/`renderMultiLinePOGroup` leave an empty placeholder div per row (`po-edit-body-<id>`/`po-terms-body-<id>`), and `togglePOEdit`/`togglePOTerms` fill it in on first open only (guarded by a `row.dataset.built` flag so re-toggling doesn't rebuild it) - reading the clicked row's own data from a new flat `window.__PO_ORDERS_CACHE` id-lookup rather than needing it passed in at render time.

No functional change - same data, same final rendered form content - verified via a scratch-server Playwright pass: both pages still fire every expected API call (just concurrently), a saved custom panel order still round-trips and applies correctly, and the lazily-built Edit/Terms panels populate with the correct row data on first open and survive being toggled closed and reopened without re-fetching or duplicating content.

## Salary Report: fixed an absurd department total (2026-10-04)

Reported directly by the repo owner with a screenshot: the Salary Report's "Total Current" column showed a ~26-digit number (e.g. ₹2,50,00,00,...,000) for one department instead of a real rupee figure.

**Root cause, traced end to end and confirmed against this app's actual DB driver (`node:sqlite`).** `employees.monthly_salary` is a `REAL`-affinity column - binding a well-formed numeric string like `"25000"` auto-converts to the number `25000` on write, but `PUT /hr/employees/:id` (the Edit Employee save) wrote `monthly_salary` straight through from the request body via `pick('monthly_salary', existing.monthly_salary)`, which only falls back to the existing value when the field is `undefined` - an empty string from a blank `type="number"` input (e.g. opening Edit on an employee whose salary was `NULL`, which renders the input blank, then saving without touching it) counts as "provided." `""` isn't a well-formed numeric literal, so SQLite left it stored as literal TEXT instead of converting it - unlike `POST /employees`, which already did `monthly_salary || 0` and was never affected. `GET /hr/salary-report`'s department aggregation (`summarize()`) then read that column straight into a plain `currents.reduce((s, v) => s + v, 0)` with no `Number()` coercion - the moment the reduce hit that one text-typed value, JS's `+` operator silently switched from numeric addition to string concatenation for the rest of that department's employees, producing exactly this kind of garbled digit-string total. `referral_incentive_amount` on the same route had the identical unguarded `pick()` pattern and was fixed the same way, even though it hadn't yet surfaced a visible symptom.

**Fix, three layers, same `routes/hr.js`/`db/index.js`:**
1. `PUT /employees/:id` now uses a new `pickNum(key, fallback)` for both fields - a blank/undefined value falls back to the existing stored value (same "blank cell never overwrites an existing value" rule the bulk-upload importers already use) rather than being written through as-is; a real value is `Number()`-coerced.
2. `GET /hr/salary-report` now builds `current_salary`/`proposed_salary` as `Number(...) || 0` once, at the row level, before `summarize()` ever sees them - so even a still-corrupted row (on data written before this fix) can't poison a department's total; it just reads as ₹0 for that one employee instead.
3. New `repairCorruptedEmployeeNumericFields()` in `db/index.js` (called from `server.js` on every boot, same idempotent pattern as every other bootstrap) resets any already-corrupted `monthly_salary`/`referral_incentive_amount` from TEXT back to numeric `0` - `typeof(col) = 'text'` can only ever match a value like this (a real number in a REAL-affinity column always reads back `'integer'`/`'real'`), so this can't touch a legitimate figure. Since the original salary value is already gone (overwritten, not just misread), this can only restore the field to a sane *type*, not recover the number it used to hold - whoever manages Payroll should re-check and re-enter the correct salary for any employee whose figure looks wrong after this ships.

Verified end-to-end on a scratch server: reproduced the exact corruption via direct SQL (confirmed `typeof` came back `'text'`), confirmed the pre-repair report already computed a sane per-department total (₹0 for the bad row, not a garbled string) thanks to fix #2 alone, restarted the server and confirmed the boot-time repair (#3) healed the row back to numeric `0`, and confirmed fix #1 by PUTting a blank `monthly_salary` against a real employee and verifying their existing salary was preserved rather than overwritten - then confirmed a genuine new value still saves normally. Final Salary Report screenshot showed every department total, min and max as a normal rupee figure.

## Offers: Standard Templates, Admin-only (2026-10-06)

Requested directly by the repo owner - a way to save a reusable "standard" Offer (e.g. a boilerplate set of inclusions/exclusions/terms for a common equipment type) that isn't tied to any customer, then reuse it as the starting point for a real client offer. Scoped with the owner's confirmation before building: templates are Admin-only to create/edit/delete; anyone with offer access can browse and reuse one, and the resulting offer is then fully independent and fully editable with no restrictions - reuse doesn't carry forward any lock.

**No new copy mechanism needed** - `POST /offers/:id/copy` already existed and already takes `client_id` from the request body rather than reading it off the source offer, and its INSERT never writes `is_template` (so a copy defaults to 0, a normal offer) - so "reuse a template" is just that same existing endpoint with zero changes, and "the result is fully editable" was already true by construction, not something that needed implementing.

**Schema** - new `offers.is_template` column (plain `ALTER TABLE ADD COLUMN`, safe as-is). The harder part: `offers.client_id` was `NOT NULL` from day one (every real offer always had a customer) - a template has no customer, so that constraint had to come off. SQLite has no `ALTER TABLE DROP CONSTRAINT`, so `migrateOffersClientIdNullable()` in `db/index.js` rebuilds the table (same table-rebuild pattern `migratePurchaseOrdersDropPoNoUnique()` already used for dropping `po_no`'s UNIQUE constraint) - but built generically off the live table's own `PRAGMA table_info()`/`PRAGMA foreign_key_list()` rather than a hand-transcribed column list, since `offers` has picked up roughly 20 columns since the base schema and hand-copying them risked silently dropping one.

**Three real bugs found and fixed while building the migration, only on the upgrade path (a fresh install's schema.sql already has nullable `client_id`, so none of these ever showed up against a brand-new database - only against a simulated pre-migration copy of a real database with existing offer rows and the offer-immutability triggers from an earlier feature already installed):**
1. The offer-immutability triggers (`trg_offers_locked_*` on `offers` itself, plus 15 more generated per-child-table triggers whose bodies reference `offers`) blocked the table rebuild outright (SQLite refuses to drop a table another trigger's body still names) - fixed by refactoring the child-trigger generation into a reusable `createOfferChildLockTriggers()` function, dropping all 17 triggers at the start of the migration's transaction, and recreating them (via `raw.exec(schema)` plus that function) once the rebuild is done.
2. A `const`/function-ordering bug - the migration function was originally placed before the `const OFFER_CHILD_LOCK_TABLES` array it depends on was declared, which would have thrown `ReferenceError: Cannot access before initialization` the moment it ran (function declarations hoist with their body; `const` doesn't). Fixed by moving the function and its call to after that declaration.
3. `FOREIGN KEY constraint failed` on the rebuild itself - `offers` has a self-referential FK (`parent_offer_id REFERENCES offers(id)`) plus every child-lock table's own FK into it, and this file sets `PRAGMA foreign_keys = ON` globally at the top, so the `DROP TABLE`/`RENAME` sequence tripped enforcement even though no row actually violates anything. Fixed per SQLite's own documented table-rebuild procedure: `PRAGMA foreign_keys = OFF` (outside the transaction - it's a no-op inside one) before the rebuild, a `PRAGMA foreign_key_check(offers)` right after as a correctness guard, then `PRAGMA foreign_keys = ON` to restore enforcement.

**Guards** - `ensureEditableVersion()` (`lib/offerVersioning.js`, the one chokepoint most content-mutating offer routes already funnel through) gained an `isAdmin` parameter and blocks a non-Admin editing a template there. That alone was insufficient for `PUT /:id` (header edit) specifically, since it only calls `ensureEditableVersion` when the offer isn't already in Draft status - and a template never leaves Draft (Mark Sent/Confirm Order are both hard-blocked for templates) - so `PUT /:id` got its own standalone, unconditional guard too. Found via direct testing (not Playwright) that a non-Admin could edit a template's subject before this second guard was added.

**Frontend** (`public/js/app.js`) - new "Offer Templates" panel at the top of the Offer Field Options page: Admin-only "New Template" creation, a table of existing templates with "Create Offer from Template" (routes into the existing copy panel) for everyone with offer access, and Admin-only Edit/Delete. The Offer Builder itself hides the Contact Person/Phone/Email fields and the Mark Sent/Confirm Order buttons when viewing a template (Download PDF stays available - harmless local preview).

Verified end-to-end twice: once against fresh databases (full CRUD/guard/copy matrix - all 9 mutating offer routes correctly 403 a non-Admin on a template and succeed for Admin; a non-Admin's copy of a template to a real client is fully and freely editable), and a second time against a simulated pre-migration legacy database (real NOT NULL `client_id`, no `is_template` column, existing offer rows, immutability triggers already installed) specifically to validate the upgrade path - confirmed the migration runs clean (`PRAGMA foreign_key_check` empty), both pre-existing legacy rows survive with identical data, the lock triggers still fire correctly post-rebuild, and the same guard/copy matrix holds against the now-migrated database.

## Purchase Order item picker: dropdown walking down the page with every keystroke (2026-10-12)

Reported directly by the repo owner with a screenshot - typing into the New Purchase Order item search box opened the suggestion dropdown far down the page (near the "Purchase Orders List" panel), nowhere near the input, and it moved further away with every character typed.

The other 5 (`todo`, `leave_request`, `salary_advance`, `salary_schedule`, `referral_incentive`) have no separate human-facing document number even in the "correct" `describeEntity()` formatting, so the `#id` fallback was never actually wrong for those.

**Fix** - new `resolveEntityRef(entityType, entityId)` in `lib/approvals.js` (same file, no new module, no require-cycle risk since `routes/approvals.js` already requires this file, not the reverse) - one lightweight single-column SQL lookup per entity type for the 10 confirmed-wrong types, returning `null` for anything else so `notifyNewPendingStep()` falls back to the original `'#' + entityId'` exactly as before for the 5 types that don't need a fix. Deliberately not a full port of `describeEntity()` - just the one field this notification actually needs.

Verified end-to-end on a scratch server: seeded one real row per entity type (PO/PR/GRN/Purchase Invoice/Expense Voucher/FG Dispatch/Sale Rejection MRN/Service Request/Foreign Payment/Salary Hike Cycle) and called `resolveEntityRef()` directly for all 10, confirming each returns the exact real document number (e.g. `PO-TESTREF`, `PO-TESTREF / Test Item` for GRN) rather than a bare id; confirmed the fallback returns `null` for an unmapped type (`todo`) and for a nonexistent id, both correctly falling through to the unchanged `'#'+id'` path; confirmed the real `startApproval()` pipeline runs end-to-end with no exception for a genuine `PurchaseOrder` chain start against the seeded PO.
